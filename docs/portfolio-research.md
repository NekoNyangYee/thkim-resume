# 포트폴리오 조사 및 설계 방향

조사일: 2026-11-07 (한국 시간)

## 1. 목표와 포지셔닝

사용자 조건은 React 19로 제작하며 프론트엔드가 주분야이고 백엔드·풀스택 경험도 함께 보여주는 것이다.

권장 방향은 **프론트엔드를 중심으로 서비스 전체 흐름을 이해하고 구현하는 개발자**다. 실제 자기소개 문구는 경력과 프로젝트를 확인한 뒤 확정한다.

화면에서는 프론트엔드 결과와 사용자 경험을 먼저 제시하고, 프로젝트 상세에서 API·데이터 모델·인증·배포까지 연결한 경험을 설명한다. 기술 이름의 개수보다 어떤 문제를 끝까지 해결했는지가 중심이다.

이 문서의 섹션 순서와 프로젝트 수량은 조사 자료를 바탕으로 한 설계 제안이다. 보편적인 채용 기준이나 합격 조건은 아니다.

## 2. 조사 근거와 적용 판단

### 빠르게 확인 가능한 작업 증거

[GitHub 공식 가이드](https://docs.github.com/en/account-and-profile/tutorials/using-your-github-profile-to-enhance-your-resume)는 짧은 소개, 기술, 경험, 대표 작업을 정리하고 지원 직무와 관련된 프로젝트를 선택하도록 안내한다. 저장소에는 기능 설명, 실행 방법, 데모, 테스트 안내를 준비하도록 권한다. 프로필 고정 저장소 권장 수량은 3~5개다.

개인 웹사이트의 첫 버전에는 **대표 2~3개를 깊이 소개하고 나머지는 보조 목록으로 제공**하는 방식을 제안한다. 2~3개는 구현과 콘텐츠 작성 범위를 조절하기 위한 제안이며 GitHub가 웹사이트에 요구하는 수량은 아니다.

[Harvard 커리어센터](https://careerservices.fas.harvard.edu/resources/portfolio-tools/)도 포트폴리오를 기술과 성과를 제시하는 수단으로 설명하고, 코딩·기술 작업을 보여주는 플랫폼으로 GitHub Pages를 소개한다. 특정 도구가 채용상 우위를 보장한다는 의미는 아니다.

### 화면과 해결 과정을 함께 제시

[NN/g UX 포트폴리오 가이드](https://www.nngroup.com/articles/ux-design-portfolios/)에서는 프로젝트의 맥락과 과정을 사례로 전달하는 방법을 다룬다. UX 직무 자료이므로 개발자 채용 통계로 일반화하지 않는다. 다만 개발 프로젝트에서도 결과 화면에 본인의 판단과 기여를 연결하는 구성은 참고할 수 있다.

### 사이트 자체의 완성도

[W3C 접근성 개발 가이드](https://www.w3.org/WAI/tips/developing/)는 의미 있는 문서 구조, 이미지 대체 텍스트, 입력 라벨, 키보드 조작 등을 안내한다. 이를 구현하면 방문자가 포트폴리오를 더 쉽게 이용할 수 있다.

[Google Core Web Vitals 문서](https://developers.google.com/search/docs/appearance/core-web-vitals)는 로딩·반응성·레이아웃 안정성을 LCP, INP, CLS로 설명한다. 구현 후 점검할 기준으로 활용하며, 점수 자체가 채용 결과를 대표하지는 않는다.

## 3. 추천 정보 구조

| 순서 | 섹션 | 전달할 내용 | 준비 자료 |
| --- | --- | --- | --- |
| 1 | 첫 소개 | 이름, 주력 직무, 강점 한 문장 | 사실에 근거한 소개 문구 |
| 2 | 대표 프로젝트 | 만든 서비스와 담당 역할 | 화면, 요약, 기간, 역할, 결과 |
| 3 | 기술과 근거 | 기술을 실제로 사용한 경험 | 기술별 프로젝트·해결 사례 |
| 4 | 경험·소개 | 배경과 일하는 방식 | 경력, 교육, 협업 중 관련 내용 |
| 5 | 연락·이력서 | 더 확인하고 연락할 경로 | 이메일, GitHub, 이력서 |

첫 화면에는 프로젝트로 이동하는 링크를 제공한다. 소개 다음에 작업 증거를 확인할 수 있도록 프로젝트를 앞에 배치한다.

사진, 블로그, 수상, 오픈소스, 자격증은 실제 자료가 있고 직무와 관련될 때 추가한다. 경력·교육 내용이 짧다면 소개에 합친다. 내비게이션은 `프로젝트 / 기술·경험 / 소개 / 연락` 정도로 시작할 수 있다.

## 4. 프로젝트 작성 기준

### 목록 카드

- 프로젝트 이름과 해결하는 문제 한 문장
- 실제 서비스 화면 또는 핵심 동작 이미지
- 개인/팀 구분, 기간, 본인 역할
- 핵심 기술 몇 가지
- 상세 보기, 데모, 저장소 링크 중 실제 제공 가능한 것

비공개 코드나 운영이 종료된 데모는 상태를 명시한다. 내용 없는 버튼이나 작동하지 않는 링크는 배치하지 않는다.

### 상세 사례

1. **배경과 문제**: 누구의 어떤 불편을 해결하려 했는가?
2. **담당 범위**: 팀 결과 중 본인이 설계·구현한 것은 무엇인가?
3. **핵심 흐름**: 사용자는 어떤 순서로 서비스를 이용하는가?
4. **기술 선택**: 제약과 대안은 무엇이고 왜 이 방법을 선택했는가?
5. **문제 해결**: 증상 → 원인 확인 → 대안 비교 → 구현 → 검증.
6. **결과**: 화면, 동작, 테스트, 측정 자료 등 확인 가능한 근거.
7. **회고**: 남은 한계와 다음 개선점.

`기여도 80%`만 쓰는 것보다 `검색 UI, URL 필터 동기화, API 오류 처리 구현`처럼 담당 기능을 구체적으로 설명한다. 개선 수치에는 측정 환경·도구·비교 조건을 함께 적는다. 수치가 없다면 실제 해결한 오류나 완성한 흐름을 설명하고 수치를 만들지 않는다.

```text
프로젝트명:
기간 / 인원:
사용자와 해결할 문제:
나의 역할과 구현 범위:
주요 사용 흐름:
기술과 선택 이유:
가장 어려웠던 문제:
원인을 확인한 방법:
고려한 대안과 선택:
결과와 확인 자료:
남은 한계 / 개선 계획:
데모 / 저장소 / 화면 자료:
```

## 5. 프론트엔드와 풀스택 역량 연결

| 역량 | 제시할 수 있는 증거 | 설명할 질문 |
| --- | --- | --- |
| UI | 반응형 화면, 컴포넌트 구조 | 화면 변화와 재사용을 어떻게 처리했는가? |
| 상태·데이터 | 검색, 필터, 캐시, 비동기 처리 | URL·로컬 상태·서버 데이터를 어떻게 나눴는가? |
| 사용자 경험 | 로딩, 빈 결과, 오류, 입력 검증 | 정상 동작 외 상태도 사용할 수 있는가? |
| 접근성 | 키보드 흐름, 의미 있는 HTML | 마우스 없이 주요 기능을 쓸 수 있는가? |
| 성능 | 같은 조건의 전후 측정 | 병목을 어떻게 발견하고 검증했는가? |
| API | 요청·응답 예시, 서버 검증 | 클라이언트와 서버의 책임은 무엇인가? |
| DB | 테이블 관계, 조회 개선 | 데이터 모델이 기능과 어떻게 연결되는가? |
| 인증·인가 | 로그인·권한 검사 흐름 | 서버에서 접근 권한을 어떻게 확인했는가? |
| 운영·협업 | 배포 과정, PR, 이슈, 리뷰 | 오류와 변경을 어떻게 관리했는가? |

모두 채워야 하는 체크리스트가 아니다. 실제 수행한 작업 중 강점이 드러나는 것을 선택한다. 공개 자료에는 키·토큰·개인정보를 포함하지 않는다.

기술 섹션은 기준이 모호한 `React 90%` 막대 대신 `React — 프로젝트 A의 검색·필터 구현`처럼 사용 근거를 연결하는 방식을 제안한다.

## 6. 기술 구성과 페이지 전략

설치 환경: React 19.3.1 / React DOM 19.3.1 / TypeScript 7.0.2 / Vite 8.3.6. Node.js 22.14.0에서 설치하고 기본 템플릿의 타입 검사와 프로덕션 빌드를 확인했다.

[React 공식 문서](https://react.dev/learn/build-a-react-app-from-scratch)는 직접 구성하는 앱에 Vite 등의 빌드 도구를 안내한다. React는 프레임워크 사용도 권장하므로 Vite가 모든 서비스의 정답이라는 뜻은 아니다. 현재는 학습과 작은 개인 포트폴리오 구성을 위해 선택했다.

- 초기 콘텐츠는 코드로 관리하고 별도 백엔드 없이 시작할 수 있다.
- 콘텐츠가 짧으면 한 페이지 내 섹션 이동으로 구성한다.
- 상세 사례가 길어지면 `/projects/프로젝트명` 같은 별도 페이지를 검토한다.
- 상태 관리·애니메이션·UI 라이브러리는 실제 요구가 생길 때 선택한다.
- 상세 페이지별 검색 노출과 공유 미리보기가 중요하면 프리렌더링·정적 생성을 검토한다.
- SPA에서 클라이언트만으로 OG 태그를 변경하면 일부 공유 크롤러가 읽지 못할 수 있어 확인이 필요하다.

[Google SEO 가이드](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)를 참고해 명확한 제목·설명·링크를 준비한다. 검색 순위는 보장할 수 없다.

## 7. 첫 버전 범위와 우선순위

**첫 버전:** 짧은 소개, 대표 프로젝트 2~3개, 기술 사용 근거, 관련 경험, 이메일·GitHub·이력서 연결, 모바일 대응.

**자료가 있으면 추가:** 기술 글, 오픈소스 기여, 아키텍처 그림, 짧은 시연 영상, 영어 콘텐츠.

**초기 보류:** 관리자 CMS, 방문자 로그인, DB가 필요한 연락 폼, 복잡한 3D 인트로, 목적 없는 차트·애니메이션. 콘텐츠나 운영에 필요해질 때 다시 판단한다. 모션을 넣는다면 `prefers-reduced-motion` 설정도 존중한다.

## 8. 완성 후 검증 기준

- 모바일에서 가로 스크롤 없이 읽히는가?
- 첫 화면에서 주력 직무와 대표 작업을 찾을 수 있는가?
- 프로젝트별 본인 기여와 선택 이유가 명확한가?
- 키보드로 메뉴·링크·버튼을 사용할 수 있는가?
- 제목 구조, 대체 텍스트, 라벨, 포커스 표시가 적절한가?
- 데모·저장소·이력서·연락 링크가 동작하는가?
- 페이지에 맞는 제목·설명·공유 이미지를 제공하는가?
- 이미지 공간을 미리 예약해 레이아웃 이동을 줄였는가?

성능 목표는 LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하를 참고한다. Core Web Vitals 평가는 실제 방문 데이터의 75번째 백분위 기준이며 모바일과 데스크톱을 구분한다. Lighthouse 같은 실험실 결과와 실사용 데이터를 구별해서 기록한다. 신규 사이트는 실사용 데이터가 부족할 수 있다. 근거: [web.dev 임계값 설명](https://web.dev/articles/defining-core-web-vitals-thresholds), [PageSpeed Insights 설명](https://developers.google.com/speed/docs/insights/v5/about).

현재는 기본 템플릿 설치와 조사 단계다. 개인 포트폴리오 화면의 브라우저·접근성·성능 검증이나 외부 배포는 아직 진행하지 않았다.

## 9. 다음 단계에 필요한 자료

1. 공개할 이름·닉네임과 희망 직무
2. 대표 프로젝트 2~3개의 개요와 실제 담당 범위
3. 데모·저장소·스크린샷
4. 실제 사용한 프론트엔드·백엔드 기술
5. 관련 경력·교육·협업 경험
6. 공개할 이메일·GitHub·블로그·이력서
7. 원하는 분위기나 참고 사이트

진행 순서는 `내용 정리 → 정보 구조 → 디자인 → 구현 → 검증 → 배포`를 제안한다.
